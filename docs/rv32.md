# The RISC-V machine, and DOOM

The same filesystem runs a second computer that has nothing in common with
the first: a 32-bit RISC-V CPU (RV32IM, with multiply and divide) running
real DOOM (doomgeneric and the shareware `doom1.wad`).

The CPU is [PicoRV32](https://github.com/YosysHQ/picorv32), unmodified. It
is fetched by `scripts/fetch-picorv32.sh` at a pinned commit and synthesized
by the same Yosys script as the CHIP-8.

| | |
|---|---|
| NAND gates / flip-flops | 22,677 / 2,035 |
| RAM / ROM | 16 MB / 8 MB, as two `.mem` folders (see below) |
| Folders / symlinks | 24,882 / 50,211 |
| DOOM, first frame | 15.6 million instructions, 22 minutes |
| DOOM, each frame after that | about 1.3 million instructions, under 3 minutes |
| DOOM, the whole of demo1 | 5,026 frames, 6.4 billion instructions, about 10 days |

The times are from a run in an Ubuntu VM on an Apple M-series Mac, which for
most of the run was also running a second copy of the machine. The daemon is single
threaded, so that's one core each.

## The rule change

The CHIP-8's 4 KB of RAM is 32,768 flip-flops. 16 MB done the same way would
be 134 million flip-flops plus the gates to address them, something like a
billion folders, so this machine bends rule 2. Its RAM and ROM are
`X.mem` folders, a third primitive:

- `X.mem/data` is a regular file holding the words. The daemon maps it into
  memory.
- Symlinks `a0`, `a1`, ... give the word address, `w0`..`w31` the data to
  write and `we0`..`we3` the byte enables.
- `X.mem/r0`..`r31` read the addressed word, combinationally.
- Writes happen on the clock tick, like a flip-flop.

That is the whole exception. The CPU, its 32 registers, the multiplier, the
divider, the timer and the address decoding are all NAND gates and
flip-flops. Loading a program means writing `rv32/ram.mem/data`.

## The machine

`hw/rv32/rv32.v` wraps PicoRV32 with the two memories, a power-on reset, the
key pins and a timer:

```
0x00000000  RAM, 16 MB
0x10000000  ROM, 8 MB (the WAD; writes are ignored)
0x20000000  TIME: instructions fetched since reset / 1000
0x20000004  KEYS: one bit per key pin
```

ECALL, EBREAK, an illegal instruction or a misaligned access halts the CPU.

There is no wall clock a program can see. TIME counts the CPU's instruction
fetches, divided by 1000, with a counter made of gates. It ticks with the
program, not with the host, so every model of the machine (the Verilog, the
folders and the C reference) reads the same values at the same instruction,
and a run is exactly reproducible.

```
rv32/
  cpu/                  PicoRV32
    cpuregs_0 .. 31     x0 to x31 (cat rv32/cpu/cpuregs_10 prints a0)
    reg_pc              the program counter
  ram.mem/  rom.mem/    the memories
  instret               instructions fetched
  halted                1 once the CPU has trapped
  keys                  the key pins
```

## The software

`sw/rt` is a small runtime for picolibc. The console is a byte count and a
text buffer in RAM. The ROM holds one read-only file behind a 64-byte header
(`tools/mkrom.py` writes it), and `open`/`read`/`lseek` on that file are
memory copies. `exit` is an ECALL.

`sw/doom` builds doomgeneric for it, with 8-bit indexed color (converting
every pixel to RGB would cost about 2 million instructions per frame) and a
WAD reader that copies lumps out of ROM. The frame buffer is at 0xE00000, the
palette at 0xE10000 and a frame counter at 0xDFFFF0. `viewer/rvdoom.py` reads
them out of `ram.mem/data` whenever the counter moves.

`tools/rvref.c` is a C model of the whole machine, including which words
PicoRV32 fetches (the word after a taken branch is fetched and thrown away,
and TIME has to count it). It runs about 150 million instructions per
second, gets through the whole demo in 40 seconds, and writes the reference
frames that the folder machine is checked against.

## Verification

- `tests/rv_lockstep_verilog.py` runs the Verilog in Icarus, through
  PicoRV32's RVFI trace port, against `rvref`. Each instruction's pc, opcode
  and the register or memory it wrote must match.
- `tests/rv_lockstep_folders.py` does the same on the mounted folder machine,
  reading each register through `rv32/cpu/cpuregs_N` and each store through
  `ram.mem/data`.
- The programs are riscv-tests rv32ui and rv32um (all but `fence_i` and
  `ma_data`, which PicoRV32 doesn't implement) and two tests of our own:
  `sw/isa/mmio.S` for the I/O registers and `sw/isa/timing.S`, which reads
  TIME after every kind of control transfer so the reference has to model
  PicoRV32's fetches exactly. 50 programs, run by `tests/run_rv32.sh`.
- DOOM itself: `scripts/run-doom.sh` compares every frame the folder machine
  draws with `rvref`'s frame, byte for byte. None has differed yet.

## Running it

```sh
scripts/setup.sh rv32          # RISC-V toolchain, PicoRV32, riscv-tests,
                               # doomgeneric, doom1.wad; builds everything
tests/run_rv32.sh              # the 50 programs, Verilog and folders

scripts/run-doom.sh            # the demo; frames go to ~/nandfs-build/doom-run/frames
scripts/run-doom.sh --resume   # carry on after a stop
```

On anything other than Debian or Ubuntu, install `riscv64-unknown-elf-gcc`
and picolibc for it, then run `scripts/fetch-doom.sh` and
`scripts/build-rv32.sh`.

`run-doom.sh` saves the RAM and every flip-flop to a checkpoint every 50
frames, so a run that takes days survives a reboot.

## Playing it

`scripts/play-doom.sh` boots a playable build (`doomplay.bin`: no demo,
straight into E1M1) on a copy of the folders of its own and serves it at
http://localhost:8035. The page shows each frame as the folders finish it
and sends your keys to the machine's key pins (`rv32/keys`), which the game
reads like any other input.

Two things differ from the demo build, both in software. The game clock runs
40 times slower than TIME, so the world advances about one tic per drawn
frame instead of about forty. And a tapped key is held for two frames, so the
game gets to see it. Ctrl-C saves the machine, and
`scripts/play-doom.sh --resume` carries on without booting again.

It is not a good way to play DOOM.
